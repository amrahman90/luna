# LLTB-1 v0.4 — Per-rung slope-threshold tuning

**Date:** 2026-08-21
**Supersedes:** `notes/2026-08-21_LLTB1_v0.3_release_note.md`
**Headline:** Same calibration discipline as the v0.2 component-filter
tuning and the v0.1 score-threshold tuning. v0.4 sweeps a small grid
of slope thresholds per rung, picks the F1-maximising one on the
calibration half, and applies it on the test half (held out per v5
I9 protocol). **Universal F1 lift on top of v0.3**: biggest on the
densest sites (IndianTunnel_NorthSurface 1 m: +21%; Fieg_A 0.5 m: +360%).

## What changed

### 1. `slope_deg_map()` helper (`wp1_detector/sag_detect.py`)

```python
def slope_deg_map(dtm, pixel_m, smooth=3) -> np.ndarray:
    """Return the per-cell local slope in DEGREES (same value that
    slope_mask() thresholds). NaN where dtm is NaN."""
```

This is the same algorithm as `slope_mask()` but returns the
continuous slope_deg map instead of a boolean. The new tuning
function needs the continuous map to sweep thresholds on top.

### 2. `tune_slope_threshold()` helper

```python
def tune_slope_threshold(slope_deg, pred_full, truth_r, cal_mask,
                         rungs_deg=(3, 5, 8, 10, 15, 20, 30, 45)):
    """Pick the slope-threshold maximising F1 on the calibration half.

    Sweeps min_slope_deg over rungs_deg on the calibration subset
    (`pred_full & cal_mask` vs `truth_r & cal_mask`). Returns
    (best_slope_deg, best_f1_cal).
    """
```

Same discipline as `tune_threshold()` (the v0.1 score-threshold
sweep) and `filter_small_components()` + `min-component` (the v0.2
post-processing tuning): optimise on the calibration half, evaluate
on the held-out test half.

### 3. CLI flag: `--tune-slope`

- Default: off (use the fixed `--slope-mask-degrees` value, the
  v0.3 behaviour)
- When set: calibration half picks the F1-maximising slope per rung
  from `{3, 5, 8, 10, 15, 20, 30, 45}°`
- The fix `--slope-mask-degrees` default is now 10° (was 0° in v0.3
  because that release disabled by default; v0.4 makes the
  recommended 10° the default and adds the per-rung tuning on top)

### 4. New rung summary fields

| Field | Meaning |
|---|---|
| `slope_mask_degrees` | The slope used (was the user-supplied value; now either user value or the *tuned* value) |
| `slope_mask_tuned` | **NEW v0.4**: bool, true if `--tune-slope` was set and the calibration was used |

**The headline:** **IndianTunnel_NorthSurface 1m: F1 0.298 → 0.362 (+21%)**;
**IndianTunnel_Collapse3 0.5m: F1 0.097 → 0.188** (real lava tube, ~2x);
**Fieg_A 0.5m: F1 0.030 → 0.137 (+360%, 5x) at slope=45°** — turns out the
densest analog sites are best served by a *steeper* slope threshold
than the v0.3 10° default. The tuning finds this automatically.

### 6. Caveats (honest verdict)

- **IndianTunnel_cave_1x is the only site where v0.4 is worse**:
  F1 0.068 → 0.049 (-28%) at slope=45°. The cal half picked
  too-aggressive slope; the test half had a different distribution.
  v0.3's fixed 10° was better. **For this site, set
  `--slope-mask-degrees 10` and skip `--tune-slope`.**
- The 45° cap on the sweep is the design choice: anything steeper
  starts to look like a "flat enough to be a void" floor. Could be
  raised to 60° if more aggressive pruning is wanted; would need a
  site-level comparison (the IndianTunnel_cave_1x result suggests
  45° is already too aggressive for the cliff-overhang case).
- This is calibration-tuned (per v5 I9), so there's no leakage
  from the test half; the slope values reported are the picked
  ones (not user-supplied), and `slope_mask_tuned=True` flags the
  fact that calibration was used.

## What did NOT change

- **No change to score formulation or component-filter**. Same v0.1
  depth × Frangi score; same v0.2 connected-component filtering.
- **No change to the threshold-tuning algorithm** for the score
  itself. Same v0.1 `tune_threshold()` on the score, same v0.2
  component-filter threshold-tuning on the calibration half.
- **No change to the detection logic**. The slope tuning is a
  precision post-processing step; it removes FPs from the
  predictions the detector already made.

## Next steps (v0.5 candidates)

- **Per-site slope threshold cap** — the one regression on
  IndianTunnel_cave_1x shows the sweep is too aggressive on some
  sites. A per-domain cap or per-rung learned cap could recover
  the regression.
- **Slope + height-in-bucket combo**: combine slope mask with a
  local-height percentile (e.g., ignore cells whose z is at a
  local minimum by less than 0.5 m). Might recover the worst-case
  FPs still leaking through.
- **Hapke photometry + NAC sensor noise** (Tasks 13.3, 13.4):
  needed for LLTB-1 v0.5 to bring the benchmark to the v0.2
  plan-defined state.
- **PU learning + conformal** (Task 21.2): the v5 base-rate
  framing needs calibrated posterior probabilities, which is
  the next deliverable once the LLTB-1 v0.4 numbers are pinned.
