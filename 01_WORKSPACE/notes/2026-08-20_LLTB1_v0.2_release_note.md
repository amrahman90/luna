**Date:** 2026-08-20

**Author of code:** LUNARVOID agent (Ahnaf181419)
**Supersedes:** LLTB-1 v0.1 (see paper1_resolution_limits/main.md)

## What changed

Two surgical improvements to the WP1 LLTB-1 pipeline:

### 1. Connected-component post-processing (sag_detect.py)

A new filter that drops connected components smaller than N cells
before F1 is computed. This is the precision lift named in the
G0' report as the highest-leverage v0.2 improvement.

- New CLI flag: `--min-component N` (default 5)
- New helper: `filter_small_components(mask, min_size)` in
  `code/wp1_detector/sag_detect.py` (8-connectivity, NaN-safe)
- New rung summary fields (in sag_summary.json):
  `f1_test_raw` (before post-processing), `min_component` (the
  hyperparameter that produced these results)
- New output GeoTIFF: `<outdir>/pred_<rung>m.tif` — the
  post-component-filter prediction mask, so the post-processing
  is independently verifiable
- Prints BOTH raw and post-filter F1 in the run log for comparison

Honest results (test-split F1):

| Site                | Rung  | F1 raw | F1 post-cc | Notes |
|---------------------|-------|--------|------------|-------|
| IndianTunnel_NorthSurface | 1 m | 0.2771 | **0.2772** (min=10) | cliff site, big void regions — filter doesn't hurt |
| IndianTunnel_NorthSurface | 2 m | 0.1622 | 0.0000 (min=10) | too aggressive; try min=3 |
| IndianTunnel_NorthSurface | 2 m | 0.1622 | 0.0571 (min=3) | still loses the small TP |
| IndianTunnel_Collapse3    | 5 m | 0.0714 | 0.0714 | recall=1.00 unchanged |
| Fieg_A             | 5 m | 0.0132 | 0.0132 | filter doesn't lift at small sites |
| Kingsbowl          | 5 m | 0.0019 | 0.0019 | worst case; filter not the bottleneck |

**Verdict:** The connected-component filter is a robust, audit-able
post-processing step, but it gives no headline F1 lift on the
current LLTB-1 sites. The precision bottleneck is not
single-pixel artifacts — it's large, connected regions of
low-but-not-zero score that map onto gentle slopes. A v0.3
precision lift would need slope-aware masking or a higher
score-threshold tuned per-rung. The filter is still useful as a
documented post-processing step for the audit trail.

### 2. f32-dir auto-discovery (run_lltb1.py)

A 22-line patch that handles the "no .f32 files in --f32-dir"
failure mode gracefully:

- If the user-supplied --f32-dir is empty (the common failure
  mode when a background process strips the symlink), search the
  canonical layout before raising:
  - `~/lunarvoid/data/analog/<site>/*.f32`
  - `~/lunarvoid/data/analog/<site>/*/*.f32`
  - Also tries stripping trailing suffixes (`_10x`, `_1x`,
    `_full`, `_topo`, `_Mesh`) from the site name (e.g.
    `IndianTunnel_cave_10x` → searches `IndianTunnel_cave_10x/`
    AND `IndianTunnel_cave/`)
- Emits a clear "auto-discovered N .f32 files in /path" message
  so the user knows the run is using a non-default source
- If nothing is found, raises `SystemExit("Did the .rar get
  extracted?")` — the previous error message ("no .f32 files
  in <path>") was not actionable

**Verified:** stripping the symlink and re-running the LLTB-1
pipeline no longer fails with "no .f32 files"; the 1.7 GB
IndianTunnel_full_10x.f32 is auto-discovered under
`~/lunarvoid/data/analog/IndianTunnel_cave/Full/`.

## What did NOT change (and why)

- **No change to `sag_detect` score formulation.** The
  depth × Frangi score is the right shape but too generous. A
  precision lift needs new features (slope-aware local mask,
  planar-fit residual) — that's a v0.3 task, not v0.2.
- **No change to `gate_recover`/`whitebox` paths.** Two
  pre-existing bugs in `wp1_ladder/degrade.py` (matplotlib
  `Axes` is no longer subscriptable in matplotlib >= 3.8) and
  one in `wp2_sag/sag_search.py` (LUNA-7 sentinel handling)
  were observed but not fixed in v0.2; they're documented in
  the session 4 notes for the next sprint.
