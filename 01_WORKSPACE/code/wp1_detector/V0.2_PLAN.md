# LLTB-1 v0.2 Backlog Plan — Connected-Component Post-Processing
## Forward-Looking Iteration (preparation during Paper 1 review)

> **Status:** DRAFT (paper-under-review prep). This is a backlog plan for
> the next LLTB-1 iteration that re-prioritises connected-component
> post-processing. Note: a "v0.2" was already shipped 2026-08-20
> (`notes/2026-08-20_LLTB1_v0.2_release_note.md`) that shipped a
> `--min-component N` flag and a `filter_small_components()` helper in
> `code/wp1_detector/sag_detect.py`. That v0.2 was **correct but
> insufficient** — v0.4 showed the precision ceiling is set by slope
> not by component-size (`notes/2026-08-21_LLTB1_v0.4_release_note.md`).
> This plan covers the **next** iteration's v0.2 backlog items that
> build on v0.5's sensor+illumination ladder.

## 1. Goal

Lift LLTB-1 **precision on the predict-all-overflagging failure mode**
(seen at the threshold=0 baseline before any score threshold). The v0.4
slope-tuning was the largest single lift; this iteration asks whether
a per-rung **area-aware** connected-component filter — tuned on the
calibration half and applied to the test half — closes the remaining
gap on the worst-case analog sites (IndianTunnel_Collapse3 2 m rung was
the regression rung in v0.4 → 0.057 at min=10; should improve most).

## 4. Algorithm changes

### 4.1 Per-rung `cc_area_min` table

Replace the single-scalar `--min-component N` flag with a per-rung table
that maps rung resolution → minimum connected-component area:

| Rung (m) | `--cc-area-min` default | Rationale |
|----------|-------------------------|-----------|
| 0.5 | 50 | Tubular features at 0.5 m are ~5×10 cells minimum |
| 1   | 20 | v0.2 --min-component=10 already optimal here |
| 2   | 8  | v0.2 regression on IndianTunnel_NorthSurface 2 m recovered here (was 0.057; expected ~0.13) |
| 5   | 3  | v0.2 regression at 5 m lifted from 0.071 → ~0.12 |
| 10  | 2  | Conservative; few positives exist at 10 m |

### 4.2 `--cc-threshold` decoupling

Currently v0.2's `--min-component` operates on the **post-threshold**
binary mask. Two new modes:

- `--cc-threshold 0` (default): filter the full score>0 mask before the
  F1 evaluation — captures predict-all overflagging directly. This is
  the headline precision lift; expected to drop FP count on IndianTunnel
  sites by ~50%.
- `--cc-threshold <value>`: filter the score>threshold binary mask
  (current behaviour, post-score-tuning). Default behaviour for v0.4
  slope-tuned runs.

### 4.3 Component-count audit field

`sag_summary.json` per-rung gains:

```json
{
  "cc_area_min": 20,
  "cc_threshold": 0,
  "cc_components_total": 4127,
  "cc_components_dropped": 4099,
  "cc_components_kept": 28,
  "f1_test_post_cc": 0.413,
  "f1_test_pre_cc": 0.298
}
```

The `cc_components_dropped / cc_components_total` ratio is itself a
diagnostic — a near-1 ratio means the score>0 mask is almost entirely
noise (the v0.1/v0.2 honest verdict); a near-0 ratio means
post-threshold filter is a no-op (the v0.4/v0.5 verdict).

## 5. Expected F1 lift estimate (anchored to v0.4 numbers)

Anchor: v0.4 lift was +21% on IndianTunnel_NorthSurface 1m (0.298 →
0.362), +45% on IndianTunnel_Collapse3 0.5m (0.097 → 0.188), +360% on
Fieg_A 0.5m (0.030 → 0.137). Slope-tuning's biggest contribution was
on the densest sites.

The v0.2 cc-filter lift was **near-zero** at v0.4 time (the precision
ceiling was on large connected regions of low score, not on
single-pixel artifacts — v0.2 release note §1 verdict). But with
**threshold=0** mode (§4.2), the cc-filter now sees the score>0 noise
floor (the predict-all mask) directly. Estimated lift:

| Site | Rung | F1 v0.5 | Expected F1 v0.2 cc (thr=0) | Comment |
|---|---|---|---|---|
| IndianTunnel_Collapse3 | 2 m | 0.063 | **0.18** | biggest lift; thin voids survive, big slope-noise drops |
| IndianTunnel_NorthSurface | 2 m | 0.074 | **0.15** | medium lift; cliff overhang isolates thin connected void |
| Fieg_A | 0.5 m | 0.137 | 0.16 | small lift; slope already 45° dominates |
| Kingsbowl | 5 m | 0.043 | 0.06 | smallest lift; recall=1.00 bottleneck, not precision |
| Sheepridge | 5 m | 0.091 | 0.10 | similar to v0.4 slope-dominated |

**Honest caveat:** if the lift is <5% on IndianTunnel_Collapse3 2m, the
iteration is negative-result and the plan falls back to the
"cc-filter is documentation, not lift" verdict (v0.2 release note
already documented this — we're testing whether thr=0 changes it).

## 6. Test cases

### 6.1 IndianTunnel_Collapse3 2 m (the worst-case regression)

v0.4: F1 = 0.063 (slope=45°); v0.2 (--min-component 10): F1 = 0.057;
v0.2 (--min-component 3): F1 = 0.071. **Acceptance:** F1 ≥ 0.15 with
`--cc-threshold 0 --cc-area-min 8` (per-rung table §4.1). If F1 still
< 0.10, fall back to thr>0 behaviour and document negative result.

### 6.2 IndianTunnel_NorthSurface 2 m (cliff overhang)

v0.4: F1 = 0.074 (slope=30°); v0.2: F1 = 0.057. **Acceptance:** F1 ≥
0.12. Caveat: cliff overhang is 4 cells wide → at --cc-area-min=8 it
should survive.

### 6.3 Fieg_A 0.5 m (slope-dominated — should be no-op)

v0.4: F1 = 0.137 (slope=45°). **Acceptance:** F1 within ±10% of v0.4
(the slope-mask has already done the pruning; cc-filter should be a
no-op here).

### 6.4 Synthetic regression test (cheap smoke)

Synthetic 200×200 random mask with 1 planted 50-cell rectangle +
10 planted 5-cell rectangles. Run `connected_component_filter(0.0,
area_min=20)`; expect 1 component kept (the 50-cell rectangle), 10
components dropped. Run on the venv:

```
~/lunarvoid/venv/bin/python -c "from wp1_detector.connected_component_filter import connected_component_filter; ..."
```

## 7. Risk analysis — Tier-A false promotions?

The biggest risk is **not** at WP1 (the cc-filter is local to the
score>0 mask, no candidate promotion happens here). Tier-A requires
two-independent-methods agreement (registry schema); cc-filter touches
only the per-rung F1 metric and the pred_<rung>m.tif mask.

**Residual risk:** the cc-filter tightens the precision ceiling but
could mask genuine tier-B candidates by dropping a tiny connected
component that fuses into the registry. Mitigation: the cc-filter
only changes the *post-evaluation* mask; tier-B promotion requires a
separate WP3 fusion path that does not consume the per-rung mask. No
false promotions are possible from this change.

## 8. Acceptance criteria

1. **Functional:** `connected_component_filter(score, thr, area_min) ->
   (filtered, count)` round-trips a 200×200 synthetic array correctly.
2. **Lint:** flake8 / ruff clean (matches v0.5 lint).
3. **Smoke test:** `~/lunarvoid/venv/bin/python
   code/smoke_test.py` produces the documented v0.5 numbers (no
   regression on the existing pipeline).
4. **Per-site lift:** IndianTunnel_Collapse3 2 m F1 ≥ 0.15; Fieg_A 0.5
   m within ±10% of v0.4 (no regression).
5. **Audit:** `sag_summary.json` records `cc_area_min`,
   `cc_threshold`, `cc_components_total/dropped/kept`, `f1_pre_cc`,
   `f1_post_cc` per rung.
6. **Documented:** release note `notes/2026-08-XX_LLTB1_v0.2b_release_note.md`
   follows v0.4/v0.5 format; CHANGELOG entry follows the v5 §9
   append-only discipline.

## 9. Wall-time estimate

- Implementation: ~4 hours (helper function is small; per-rung table
  CLI plumbing + audit fields are ~40 lines).
- Synthetic regression test: ~5 min.
- Per-site re-run on 7 sites × 4 rungs: ~2 hours (v0.5 ladder takes
  ~15 min/site on local Tier-0 hardware; cc-filter adds ~30 sec/site).
- Verification: ~30 min.
- Documentation: ~1 hour.

**Total: ~6 hours Tier-0 compute; $0 spend.** No GPU; no rental;
no DTM re-download.

## 10. Non-goals

- Per-DTM adaptive `cc_area_min` (the per-rung table is global; per-DTM
  tuning is v0.6+ scope).
- Combining cc-filter with --tune-slope into a single joint tuning
  sweep (orthogonal; defer to v0.6+).
- Back-porting cc-filter to v0.5's pre-existing 11/11 verification
  evidence (the v0.5 numbers are frozen per release-note §guardrails).
